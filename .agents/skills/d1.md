# Kỹ Năng D1 & SQLite Engine — DustGuard VN

> **Mục tiêu**: Thao tác và kiểm chứng độ bền vững của CSDL Cloudflare D1 (`dustguard-production` trên Cloudflare / `prisma/dev.db` trên môi trường phát triển local).

---

## 1. Nguyên Tắc D1 là SSOT (Single Source of Truth)
- Toàn bộ dữ liệu nghiệp vụ của DustGuard VN (Hồ sơ, Công trình, Nhiệm vụ, Khảo sát, Minh chứng) phải được lưu trữ và truy vấn trực tiếp từ D1.
- Tuyệt đối không sử dụng mock-data khi endpoint D1 đã tồn tại.
- Mọi thao tác CREATE, UPDATE, DELETE phải được kiểm tra qua quy trình đối chứng tải lại (Mutation Oracle).

---

## 2. Quy Trình Đối Chứng Đột Biến (Mutation Verification Pattern)
Trước khi tuyên bố một tính năng ghi nhận dữ liệu hoàn tất, agent phải chứng minh được:
```text
1. CREATE:
   Gửi mutation tạo mới -> Phản hồi 201/200 -> Query lại CSDL D1 -> Bản ghi tồn tại với đầy đủ trường.

2. UPDATE:
   Gửi mutation cập nhật -> Phản hồi 200 -> Query lại CSDL D1 -> Các trường dữ liệu mới được cập nhật chính xác, trường cũ giữ nguyên.

3. DELETE / CLOSE:
   Gửi mutation đóng/xóa -> Phản hồi 200 -> Query lại CSDL D1 -> Bản ghi biến mất hoặc trạng thái chuyển sang 'CLOSED'/'COMPLETED'.
```

---

## 3. Schema & Truy Vấn Tối Ưu (Schema Guidelines)
- Schema gốc tại `app/prisma/d1-schema.sql` (46 bảng).
- Không tự ý thêm bảng mới nếu thực thể có thể ánh xạ vào bảng hiện tại.
- Luôn sử dụng Prepared Statements (`db.prepare(...)`) để chống SQL Injection.
- Sử dụng Composite Index trên các truy vấn lọc thường xuyên (vd: `[status, priority]`, `[siteId, createdAt]`).
- Tọa độ địa lý lưu dưới dạng `latitude`, `longitude` (WGS84) phục vụ tính toán bán kính Geofence $\le 50\text{m}$.
